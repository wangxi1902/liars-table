# 结构化决策依据与实时展示

这一阶段让观战者在当前头像上方看到“AI关注谁、怀疑度多少、依据哪些公开事件”，
但不会展示Prompt、模型原始回复或隐藏思维链。

## 1. 为什么不能直接展示模型理由

模型可能产生三类问题：

1. 引用不存在的事件编号；
2. 把预言家查验、狼人队友等私有信息写进公开卡片；
3. 输出很长的自由文本，前端无法稳定解析，也无法评测。

因此后端采用两层结构：

```text
DecisionBasisPayload（模型候选输出，不可信）
                 ↓ 格式校验、座位校验、事件可见性校验
SafeDecisionBasis（允许发给前端）
```

## 2. Pydantic校验和业务校验的区别

Pydantic负责检查：

- `suspicion`是不是0到100的整数；
- 最多关注三名玩家；
- 每名玩家最多引用三条依据；
- `kind`是不是允许的有限枚举。

但Pydantic不知道事件12是否真实存在，也不知道P9是否已经出局。这些属于狼人杀业务
规则，需要`build_safe_decision_basis`根据当前`DecisionRequest`再次校验。

一句话记忆：**类型正确不等于业务合法。**

## 3. 如何防止私有信息泄露

模型只提交事件编号和依据类别，不提交可直接展示的自由文本理由。后端只接受
`DecisionRequest.transcript`中的编号，并从该公开时间线重新取得摘要：

```text
模型：event_id=18, kind=vote_pattern
后端白名单：[18] P6投给了P2
前端：#18 · 票型 / P6投给了P2
```

模型即使提交私有笔记编号或伪造编号，也会被丢弃。当前公开类别包括发言、票型、
身份声称和一般行为。

从v0.6e开始，最终展示的怀疑度不再采用模型临时分数，而由跨回合
`SuspicionLedger`计算；详见`07-跨回合怀疑度账本.md`。

## 4. 实时流如何保持顺序

一局游戏现在有三种流消息：

```text
decision_trace  LangGraph正在执行哪个阶段
decision_basis  已通过安全校验的判断依据
普通事件        发言、投票、死亡、系统事件
```

会话层为它们分配统一的`stream_seq`。React按这个游标排队播放，因此会看到：

```text
头像上浮 → 准备上下文 → 请求模型 → 校验输出
         → 展示判断依据 → 播放正式发言
```

断线重连时，HTTP快照返回`stream_cursor`，WebSocket只继续处理更大的游标，避免重复。

## 5. 为什么当前只实时展示发言思考

白天发言是串行的，正好对应“当前一个头像上浮”。投票使用`asyncio.gather`并发执行，
可能同时有多个AI思考。如果强行复用单头像卡片，会快速闪烁且无法阅读。

因此当前方案是：

- 发言依据：实时展示；
- 投票依据：后端结构已支持保存，留给后续复盘页面；
- 夜间私有决策：暂不进入公开依据，防止泄露身份和策略。

## 6. 前端职责

前端不判断事件是否合法，只做四件事：

1. 按`stream_seq`排队；
2. 根据Trace更新“正在思考”的阶段文字；
3. 把`focus_players`渲染为怀疑度和证据列表；
4. 把卡片定位到当前上浮头像上方。

关键业务逻辑仍在后端，避免不同页面出现不同的安全规则。

## 7. 学习检查点

完成本节后，应该能回答：

1. 为什么JSON格式正确后还要做一次业务校验？
2. 为什么证据摘要由后端公开时间线生成，而不是直接使用模型理由？
3. `stream_seq`与游戏事件自己的`seq`分别解决什么问题？
4. 为什么并发投票不适合复用单个“当前头像”动画？

可选练习：给`EvidenceKind`增加一个`contradiction`类别，并补一条解析测试和前端中文
标签；不要改变现有事件可见性校验。
